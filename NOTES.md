# Talent Dex — build notes

Decisions, things skipped, and known data gaps, written as the build goes.

## Setup

- **keys.env format.** The file came as label comments followed by bare values, which dotenv
  can't read. It was rewritten in place to `GITHUB_TOKEN=`, `GEMINI_API_KEY=`, `PDL_API_KEY=`
  (comments kept, values unchanged). `DATABASE_URL` is not set, so the pipeline writes JSON only
  until it is added (see milestone 5).
- **Design file location.** The approved design was at the repo root under its export name; it was
  moved to `design/talent-dex-v3.html` as the brief expects. `scripts/extract_design.py` writes the
  readable markup and logic to `design/extracted/` (`markup.html`, `component.js`).
- **Next.js 16.4 / React 19.3 / Tailwind 4.3.** Scaffolded with create-next-app, which turns on
  Cache Components. Consequences: the matches page wraps its client app in `<Suspense>`
  (`useSearchParams`), and API routes that read files run per request.
- **Tailwind without preflight.** The design was drawn against browser defaults (it only resets
  `body{margin:0}`), so `globals.css` imports Tailwind's theme and utilities but not preflight. The
  design's `<style>` block is copied verbatim; only the font stacks point at next/font variables.
- **Fonts** load through `next/font/google` (Fredoka, Nunito, Geist Mono). They are downloaded at
  build time and served locally, so the demo does not depend on venue wifi. SVG `<text>` uses
  `.svg-mono` / `.svg-body` classes because next/font renames the families.
- **Gemini model.** `gemini-3.8-flash` (`gemini-2.5-flash` is no longer offered to new keys).
- **People Data Labs budget.** The key has 100 lookups in total; a single 404 probe used one. The
  pipeline caps PDL calls, prioritises builders, caches raw JSON per LinkedIn URL and never calls
  the same URL twice.

## Milestone 1 — UI on sample data

- **Architecture.** `lib/viewmodel.ts` is a TypeScript port of the design's `renderVals()` and
  `profile()`; `components/dex/DexApp.tsx` ports the `Component` class (state, timers, FLIP morph,
  slide, burst, copy, keyboard). Components only render view models.
- **Sample data** (`data/sample.json`) is generated by `scripts/port-sample.mjs` from the design's
  `candidates()`. It is in the final data shape, so the design's free-text criteria notes
  ("6 of 7 projects use PyTorch or TensorFlow") became the counts they describe
  (`codeProjects`, `typeProjects`) and every note is computed by the app.
- **Scores are computed, not copied.** The design's hand-made scores (96, 91, 88…) are replaced by
  the brief's formula, so the sample ranks Maya 100, Arjun 87, Priya 82, and so on. Two criteria
  differ from the design's hand labels: Ethan's ML is *Close* (3 of his 8 projects have ML code,
  which is under half), and Priya's location is *Does not match* (London is about 165 km from
  Toronto, past the 150 km "Close" radius; the design hand-labelled it "about two hours away").
  Criterion notes are generated from counts ("6 of 7 projects have ML / AI code") rather than
  copied from the design's hand-written text.
- **Criteria rows are dynamic.** The brief allows 1–2 skill types, so "Why X fits" shows one row per
  active criterion and the pill reads "k of N match" (N = 4 for the design's search).
- **Missing data.** A fifth status, "Not listed", is used when a criterion can't be checked (no year
  or city found); it scores 0 and names where we looked. Field notes show "Not listed" with a
  "Looked in …" line.
- **Score ring and radar numbers.** The design's own renderer drops text inside SVG `<text>`, so its
  screenshots show empty rings; the markup intends a number there, and the port renders it.
- **Screen 0** (not in the design) reuses the lid, header, card and button styles. Until milestone 4,
  `/api/parse` uses a keyword parser (`lib/parse-rules.ts`); an empty search runs the design's
  default search (ML / AI, Year 3, Toronto, Hackathon winner).
- **Additions to the design:** "Show N more builders" (24 per page), a "No builders match this search
  yet" empty state, loading/error frames (`DexStatus`), and "Not linked on Devpost" link pills. The
  shortlist is kept in localStorage and "Seen" in sessionStorage (both optional; the app works
  without storage). Sample mode pins "now" to the sample's date so "Last active" reads as designed.
- **Checks:** `npx playwright test tests/e2e/screens.spec.ts` saves one screenshot per screen to
  `docs/screenshots/`; `design/shots/` has the design file rendered the same way for comparison.

## Milestone 2 — Attribution on PlantHopper

- **Plain `git log` check.** `git log --follow -- '*UniversalControl.ino'` on
  `jello-2/PlantHopper` shows 21 commits, all by `pekachoo <jliu6162@gmail.com>` (all-time).
  Hack the Valley X's submission window is Oct 3 2025 8:00pm to Oct 5 10:00am EDT, and all 21
  commits are inside it (the last is 9:44am on Oct 5), so the window drops none of them. The
  pipeline gives the file to `pekachoo` at 100% (571 counted lines);
  `pipeline/tests/test_attribution.py` asserts the share, the 21 commits and the window.
- **Window source.** The hackathon API only gives days ("Oct 03 - 05, 2025"), so the window comes from
  the event's `/details/dates` page (`data-iso-date` on the Submissions row, with offsets). If that
  page is missing, whole days in Toronto time from the API are used and the source is recorded.
- **Identity mapping order.** (1) the GitHub account GitHub itself links to the commit email (commits
  API `author.login`) equals the GitHub link on the member's own Devpost profile; (2) a
  `…@users.noreply.github.com` address names that account; (3) exact email = the public email on
  that GitHub account; (4) within the team only: same full name, same words in another order, or the
  git name equals their Devpost/GitHub username. A lone first name ("Alice") is never matched.
  On PlantHopper all six commit identities map by (1).
- **What counts as code.** On top of the brief's exclusions, only source-like files count (docs,
  data and config don't), minified bundles are also caught by content (very long lines), generated
  files (`*_pb2.py`, `*.g.dart`, Xcode projects) are skipped, and a single file in a single commit
  counts at most 2,000 lines (a guard against notebooks with outputs and dumped data; capped lines
  are reported per repo). PlantHopper committed `node_modules` (3.15M lines) and `.next/` build output;
  both are excluded.
- **Persistence and docs per repo.** "Kept building" needs a commit after the window that touches
  counted code (README-only commits don't count). The README author is whoever added the most lines
  to the root README across all time; it counts toward Documentation when the README is > 300 chars.
  (Both rules were tightened in milestone 3; see "Attribution after review" below.)

## Milestone 3 — Full pipeline and real data

Run with `cd pipeline && .venv/bin/python -m talentdex.run` (options: `--portfolio-cap N`,
`--no-pdl`, `--no-words`, `--workers N`). Every network answer is cached under `pipeline/cache/`
(gitignored), so a re-run only redoes what changed. Output is `data/builders.json`, checked by
`talentdex/output.py` against the `lib/types.ts` shape before it is written. `npm run dev:real`
(or `DATA_SOURCE=real`) shows it; the UI needed no code changes, only the optional
`scan.order` field below. `docs/screenshots/real/` has the three screens rendered from it.

- **Which hackathons.** BUILD.md's list was searched on Devpost's hackathon API by exact title.
  Five have public galleries and are scanned: Hack the Valley X, Hack the Valley 9, Hack the 6ix
  2025, DeltaHacks XI and Hack the North 2025. UofTHacks 12 has no Devpost listing under any
  spelling we tried, and Hack the Valley 11's gallery is not published yet ("The hackathon
  managers haven't published this gallery yet"), so both are skipped.
- **Which projects.** The design's 214 is split evenly: 43 per event (215 in total). Winners
  come first in gallery order, then the rest; a project is kept only if it links a GitHub repo.
  Hack the North 2025 had 54 winners, so all 43 of its projects are winners; the other events
  are a mix. Projects without a repo link (1 to 11 per event) were passed over.
- **Who is a builder.** A team member on a scanned project with more than 0 counted lines
  mapped to them, and a public Devpost profile. 642 members → 351 builders. Members with no
  mapped code are not shown (no invented numbers).
- **Repos.** 224 repos for 215 projects; 198 analysed, 25 are gone or private, 1 is over the
  300 MB clone limit. 5,240 commits counted. Clones are full (`--no-checkout`); a partial
  clone was tried and was slower, because rename detection fetches blobs one at a time
  (171 s vs 38 s on the same repo).
- **Portfolios.** Each builder's other hackathon projects (from their own Devpost profile, up to
  `--portfolio-cap`, default 30) are attributed the same way, using that event's own window and
  team. A fast first run with `--portfolio-cap 0 --no-pdl` scored builders on their scanned
  project only; the committed data says which run made it (`pipeline/cache/steps/run.json`).
- **Attribution after review.** Two independent reviews of milestone 2's attribution, then a
  verify and repair pass, tightened these rules:
  - A file version that was already credited (same path, same content) earns 0 lines again,
    so re-adding a file or reverting doesn't double-count ("replayed" lines are reported).
  - Identities are per (email, name). An ambiguous first name stays unknown. Names in other
    scripts are compared after Unicode folding.
  - The starter-template check follows every commit before the event start through renames,
    deletes and exact copies.
  - "Kept building" means added counted lines after the end of the event's last day.
    Replayed files don't count.
  - Documentation is credited by `git blame`: more than 300 characters of the current
    README must be the builder's own.
  - Notebooks count code cells only.
  - Repos that fail for temporary reasons (rate limits, 5xx) are retried once and never cached
    as skipped.
- **Exclusions found on real data.** Three kinds of committed third-party code were credited to
  one person until they were excluded:
  - A Lens Studio project's `Cache/` folder (jasonnpan/ARchemy: 550,925 lines of compiled
    TypeScript). `Cache/`, `Support/`, `Workspaces/` and `Packages/` next to a `*.esproj` with
    `Assets/` are now excluded.
  - Packages installed with `pip install -t` for an AWS Lambda (JaydenYip3/htv_serverless:
    700,589 lines of twilio, aiohttp…). The files listed in each `*.dist-info/RECORD` are now
    vendored.
  - Django `collectstatic` output (ssadras/SafeOStroll). A folder holding Django's
    `admin/js/core.js` is build output. If that folder is also an app (it holds `.py` files,
    as in manalafzal47/htv_app), only its `admin/` goes.
  - Known gap: research code copied into a non-library folder (e.g. `ml/MST-plus-plus/` in
    one repo) still counts, since nothing marks it as third-party.
- **Classification.** Rules first (extension, path, imports, dependencies); Gemini only for files
  the rules can't place. 10,786 files: 2,644 went to Gemini in 142 batches of up to 30, and
  10,758 got a type.
  - Gemini sees paths, imports, the first lines of code and the repo's dependency names.
    Team members' names, usernames, emails and URLs are redacted from all of them.
  - Rules: stylesheets are Design, except Tailwind entry files, which are Frontend. A file
    importing an ML library is ML (a Flask route that calls OpenAI is ML). ORM models are
    Backend. `model/` and `train/` paths count as ML only in repos with other ML signals.
    pyserial is Hardware; Solidity and Terraform are Backend.
  - Gemini runs at its default thinking level. Low thinking was 5× faster but put a whole
    batch on the other side of a close call (28 per-animal modules in an animal-vision
    project: ML vs Backend), so speed comes from sending a repo's batches in parallel instead.
- **Numbers.** Card "Hackathons" is the larger of the Devpost profile's count and the distinct
  events in their analysed projects. Wins are prizes on Devpost. Repos is the public GitHub
  repo count, "Not listed" without a GitHub link on Devpost (58 builders).
- **Words.** Gemini wrote every builder's why line and summary (351 of 351) from verified facts
  only, and every number in a line is checked against those facts before it is used. A template
  line takes over when Gemini fails twice.
- **Places.** `data/places.json` gained 28 cities (Thornhill, Aurora, Whitchurch-Stouffville…
  plus Gatineau, Quebec City, Halifax, Winnipeg, Victoria, Saskatoon, Regina) and a province per
  city. City matching checks the province, so "London, England" is not London, Ontario.
  Devpost writes some locations as "Toronto, ON, CA"; CA is read as Canada.
- **Data gaps (quick run, before People Data Labs).** Of 351 builders, 41 list a school and 7 a
  year of study on Devpost. 266 have a city and 293 a "last active" date (the rest link no
  GitHub). Everything missing shows "Not listed" with where we looked.

## Milestone 4 — Search parsing with Gemini, scan replay

- **Parse order** (`lib/parse.ts`):
  1. A cached Gemini answer from `data/searches.json`, keyed by the text with case and spacing
     ignored.
  2. A live Gemini call, only when `ALLOW_LIVE_GEMINI=1`; the answer is added to the cache.
  3. The keyword rules (`lib/parse-rules.ts`), which work offline.

  The demo runs with live Gemini off, so a search that isn't cached falls back to the rules
  and never fails.
- **What Gemini sees.** Only the recruiter's text, sent through the REST API with the key in the
  `x-goog-api-key` header (never in a URL or a log), temperature 0, 20 s timeout. The answer is
  constrained by a response schema with these fields:
  - `types` (at most 2, in order of importance).
  - `year` (0 = new grad, null when not stated).
  - `location` (mapped to the `places.json` name).
  - `winner`.
  - `topic` and `topicQuery`. `topic` is a chip label of at most five words, only for
    "built this kind of project" searches. `topicQuery` is that topic as one sentence with
    acronyms spelled out ("retrieval-augmented generation… vector database"), for milestone
    5's semantic search; small embedding models miss "RAG" on its own.
- **Topic rule tightened.** The first warm-up gave the hardware chip the topic "embedded sensors
  and microcontrollers", which only repeats the Hardware type. The prompt now says skills, tools
  and parts are never a topic, and the cache was rebuilt with that prompt.
- **Cached searches.** `data/demo-searches.json` holds the demo's texts: the three chips on
  screen 0 (which now read from it), two RAG searches and a pasted job posting.
  `scripts/cache-searches.mjs` sends them to a dev server started with `ALLOW_LIVE_GEMINI=1`.
  Gemini's answers:
  - ML intern chip: ML / AI, Year 3, Toronto, winner.
  - Hardware chip: Hardware, any year, Hamilton.
  - Backend chip: Backend, new grad, Waterloo.
  - "Built a RAG pipeline": ML / AI + Backend, topic "RAG pipeline".
  - Job posting: ML / AI + Backend, Year 3 ("3rd or 4th year"), Toronto, winner ("hackathon
    winners are a plus").
- **Scan replay.** The run records the order it checked the scanned projects and which builders
  each one surfaced (`scan.order`). Silhouettes still appear in rank order with the design's
  timing. Each card is revealed when the counter reaches the project where the run found that
  builder, so a top match found late stays a silhouette until then. The counter runs to the
  real total (215 projects), and the sample, which has no crawl order, plays exactly as before.
- **Tests.**
  - `tests/e2e/api.spec.ts`: every demo search is a cached Gemini parse, an uncached search
    falls back to the rules, bad requests get a 400, and the scan carries real totals.
  - `tests/e2e/search.spec.ts`: a chip leads to screen 1 with Gemini's chips, a topic
    survives the URL, and the replay reveals cards as it goes (with `DATA_SOURCE=real`).
